# ncm-api-kit 接入评估

> 评估对象：`ncm-api-kit.zip`（2026-10-19 版，含逆向报告、接入指南、Python 客户端、Kotlin 客户端）
> 对照基线：本仓库 `main`（`NcmApi.kt` 2934 行、60+ 接口）
> 实测时间：2026-10-19，线上明文接口直连

---

## 1. 结论

**大部分不用接** —— 本仓库的接口覆盖已经超过这份 kit，且更深（eapi、FLT 一起听、听歌打卡、歌曲百科、歌词罗马音都是 kit 没有的）。

**真正值得接的只有 4 项**，按优先级：

| 优先级 | 能力 | 接口 | 本次实测 | 价值 |
|---|---|---|---|---|
| P0 | 榜单 | `/api/toplist` + 现有 `playlistDetail` | ✅ 64 个榜 | 补一整块缺失功能 |
| P1 | 搜索翻页 | `/api/search/get` 的 `offset` + `hasMore` | ✅ 306 条，翻页生效 | 现有搜索只能看前 20 条 |
| P1 | 搜歌单 | `/api/search/get` `type=1000` | ✅ 521 条 | 搜索页多一类结果 |
| P2 | 可播状态提前判定 | `privilege.st` / `privilege.pl` | ✅ | 列表里提前置灰，少一次试播失败 |

另外有两个「不是新接口、但值得抄实现」的点，见第 5 节。

## 2. kit 里有什么

| 部分 | 内容 | 对本次接入的作用 |
|---|---|---|
| `report/` 逆向报告 | weapi 算法还原、双通道、接口地图（168 条路径）、分页陷阱 | 验证我们的加密实现是否一致；接口地图可当查漏清单 |
| `guide/` 接入说明 | 9 类接口的参数/响应/坑，字段归一化表 | 参数口径参考 |
| `python/` 客户端 | 搜索/歌单/歌词/评论/榜单/扫码 + CSV 导出 | 批量导出场景可复用 |
| `android/` Kotlin 客户端 | 7 个文件，OkHttp + Gson + 协程，含签名与 Cookie 持久化 | **不建议整体接入**，我们已有等价且更深的实现 |

Kit 自述覆盖 9 类：搜索、歌曲详情、歌词、歌单、专辑、歌手、评论、榜单、用户。

## 4. 建议接入项

### 4.1 P0：榜单（唯一真正的功能缺口）

`/api/toplist` 返回榜单元信息，`tracks` 恒为 `null`，要拿歌得用榜单 id 当歌单 id 调 `/v6/playlist/detail`。

本次实测（2026-10-19）：

```
code 200  count 64
  19723756  飙升榜      100  更新27首
  3779629   新歌榜      100  刚刚更新
  2884035   原创榜      100  每周四更新
  3778678   热歌榜      200  刚刚更新
  71384707  网易云古典榜 100  每周四更新
```

接入成本：`NcmApi.toplist()` 约 20 行；UI 侧可以复用现有「歌单列表 + 歌单详情」两个页面，只需要一个入口。**几乎零新页面成本**。

建议入口：主页 `homeItems` 在「每日推荐」后加一项「排行榜」，路由 `"toplist"`。

### 4.2 P1：搜索翻页

现状：`search()` 的 `offset` 硬编码 0、`limit` 固定 20，用户看不到第 21 条之后的结果。kit 的实测口径：

| 参数 | 约束 |
|---|---|
| `limit` | **上限 100**，传 1000 返回空列表 |
| `offset` | 递增翻页 |
| `total=true` | 返回 `songCount` |
| `hasMore` | 响应自带，false 时停止请求 |

本次实测：`s=海阔天空` 共 306 条，`offset=0` 与 `offset=20` 返回不同曲目，`hasMore=true`。

改法：`search(kw, limit, offset)` 增加 offset 参数与 `hasMore` 返回值；UI 滚到底部加载下一页，`hasMore=false` 时停。

### 4.3 P1：搜歌单

`type=1000`，本次实测 `s=华语` 返回 521 个歌单，字段与 `/user/playlist` 基本一致（`id/name/coverImgUrl/trackCount/playCount`），可直接复用现有 `PlaylistItem` 与卡片组件。

搜索页加一个「歌单」分段即可，点进去走现有 `playlistDetail`。

### 4.4 P2：可播状态提前判定

kit 给的判定（比 `fee` 可靠）：

```kotlin
available = privilege.optInt("st") >= 0 && privilege.optInt("pl") > 0
```

- `pl` 是可播码率（320000 = 320kbps），**不是布尔**；
- `st < 0` 表示下架；
- 搜索接口**没有** `privilege`，此时状态未知，不要当成「不可播」。

我们现在的做法是点播时才知道能不能放（`songUrl` 失败）。接入后可在列表里提前置灰不可播曲目，减少一次失败交互。

注意只能用于「详情/歌单/专辑」返回的数据，搜索结果没有 `privilege`。

### 4.5 P3：MV / 电台 / 粉丝

接口都在（`/api/v1/mv/detail`、`/api/dj/program/detail`、`/api/user/getfollows/{uid}`），但圆屏手表的展示空间有限，优先级低。粉丝列表我们已有 `friends()`，语义上够用。

## 5. 值得抄的两个实现细节

### 5.1 空响应要显式识别

kit 指出：加密通道参数不对时，服务端返回 **HTTP 200 + 空 body**。

我们现在的 `post()` 是 `JSONObject(text)`，空串会抛异常 → 被 catch → 返回 `code=-1`，错误信息是 `Unterminated string at character 1`，看不出真实原因。

建议：

```kotlin
val text = resp.body?.string().orEmpty()
if (text.isBlank()) {
    lastError = "空响应（参数或风控）"
    return JSONObject().put("code", -1).put("msg", "empty body")
}
```

好处：连续空响应时可以触发退避，而不是当作普通网络错误重试。

### 5.2 错误码映射

| 码 | 含义 | 处理 |
|---|---|---|
| `301` | 登录失效 | 跳登录，**不要重试** |
| `404` | 内容下架/路径不存在 | 提示「内容不存在」 |
| `-110` | 无播放权限 | 置灰，不弹错 |
| `-460` | 风控 | 退避 + 提示稍后 |
| `5xx` | 网关异常 | 指数退避重试 |

我们目前只有 `lastError` 字符串，UI 层靠文案判断。建议在 `NcmApi` 里给一个 `codeOf(j)` 辅助，供 UI 做分支。

## 6. 不建议接入

| 项 | 原因 |
|---|---|
| 整体替换成 kit 的 Kotlin 客户端 | 我们已有 OkHttp 封装、Cookie 持久化、csrf 自愈、eapi/FLT 多套口径，替换是倒退 |
| 音频地址批量获取 / 批量下载解析 | kit 明确划在边界外；`privilege.pl = 0` 是版权授权结果 |
| VIP / 地区限制绕过 | 同上，且违反商店政策 |
| Banner | 手表无展示位 |
| Python 客户端的 CSV 导出 | 属桌面/脚本场景，与 App 无关 |

---

## 7. 如果只做一件事

**接榜单（P0）**。它补的是一整块用户可感知的缺失功能，且能 100% 复用现有歌单页与详情页，改动量最小、收益最直接。

搜索翻页（P1）次之，属于体验修 bug 级别 —— 现在用户搜出来的结果只有 20 条，看不到更多。
